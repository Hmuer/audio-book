# AI 有声书流水线 —— 对大模型（LLM）的需求说明

> 用途：把本清单发给模型网关，用于选型 / 配置（上下文、最大输出、超时、并发、限流、结构化输出、思考开关等）。
> 调用形态：**OpenAI 兼容** `POST {base_url}/chat/completions`，纯文本输入、JSON 输出，无多模态。

---

## 1. 总体情况

- 业务：中文长篇小说 → 自动生成有声书。识别阶段会对全书反复调用 LLM 做「结构化抽取」。
- 典型单本规模：**约 1300 章、430 万字**（例：武动乾坤 1331 章 / 433 万字）；也有 500~2000 章的书。
- 一本书识别阶段 LLM 调用量约 **1,700 ~ 2,100 次**；累计 token 粗估 **2000 万 ~ 3000 万 / 本**。
- 所有输出都要求是**严格 JSON**（我们按 Pydantic Schema 校验，失败会重试/抢救）。**不允许 markdown 代码块包裹、不允许解释性文字**。
- 语言：中文（含武侠/仙侠人名、别名、尊称、文言味对话），需要良好的中文理解与指令遵循。
- 内容：用户小说的正文（虚构文学，可能含暴力/争斗/情感等情节），**网关的内容审核不能过度拦截正常小说文本**（我们已遇到过 422 内容拒绝导致个别章节失败）。

---

## 2. 需要网关提供的硬性能力

| 能力 | 要求 |
|---|---|
| 协议 | OpenAI 兼容 `/v1/chat/completions` |
| **上下文窗口** | **≥ 64K tokens，推荐 128K**（单次输入最大约 5 万中文字 ≈ 3.5~5 万 tokens） |
| **单次最大输出** | **≥ 24,000 tokens**（对白归属一步会一次生成很长的结构化 JSON；网关若默认卡 4K/8K 会截断） |
| **单请求超时** | **不能被网关在 60s 切断**。重结构化请求常需 **30~180s**；建议 `proxy_read_timeout ≥ 600s`（我们客户端设 1200s），或支持流式保活 |
| 结构化输出 | 支持 `response_format={"type":"json_schema",...}`（最佳）或 `{"type":"json_object"}`；模型要能稳定输出符合 schema 的 JSON |
| **思考模式开关** | 支持 **关闭思考**（`enable_thinking:false` / thinking disabled），且关闭时**不得偷偷长思考**（否则会把请求拖到超时） |
| 并发 | 支持**单 key ≥ 16~32 路并发**（我们当前 `LLM 并发=16`，对白批并发=10，可上调到 24~32） |
| 限流语义 | 触发限流返回 **429 + Retry-After**；不要用 5xx/504 表示限流 |
| 稳定性 | 避免间歇性 502/504；长请求不要中途断流 |
| 温度 | 支持 `temperature`（我们用 0.1~0.2，希望可复现） |
| 流式（可选但推荐） | 支持 `stream=true`（长请求更稳，便于规避非流式超时） |

## 3. 业务场景清单（每个场景的输入/输出/规模）

| # | 场景 | 输入规模 | 输出内容（JSON） | 最大输出 | 单本调用量 | 并发 | 温度 | JSON 严格度 |
|---|---|---|---|---|---|---|---|---|
| 1 | **书籍资料生成** | 书名 + 若干章样本（约 1 万~1.5 万字）+ 可用旁白音色 | 分类/标签/卖点/简介/默认旁白音色 | 2.4K | 1 | 1 | 低 | 中 |
| 2 | **角色识别** | **按 5 万字符切片**，全书覆盖（一本约 80~90 次） | 角色列表：姓名/性别/别名/描述 | 8K | ~80~90 | 4 | 0.2 | 高 |
| 3 | **角色去重合并** | 成对角色（每批 ~20 对，约 190 对判断） | 合并/保留决策 | 16K | 10~40 | 4 | 0.1 | 高 |
| 4 | **对白归属（最重）** | 每批 4~14 章（正文 0.4万~1.2万字）+ 角色表 + 少样本 | 逐章逐句：说话人、原文锚点偏移、情绪等**嵌套 JSON** | **24K** | ~330~1300 | 10 | 0.1 | **极高** |
| 5 | **逐段情绪（MiniMax 路线）** | 每批 6 章正文 | 每句一个情绪枚举（7 类） | 8K | ~200+ | 4 | 0.1 | 高 |
| 6 | **逐段语音指令（豆包路线）** | 每批 6 章正文 | 每句自然语言语气/节奏描述 | 8K | ~200+ | 4 | 0.2 | 中 |
| 7 | **润色（diff）** | 每章正文（约 3000 字） | 修改 diff（原文→改后） | 16K | ~1300（每章 1 次） | 4~8 | 0.1 | 高 |
| 8 | **音色推荐** | 角色表 + 官方音色清单 | 角色→音色分配 | 4K | 1~2 | 1 | 低 | 中 |

> 说明：场景 4「对白归属」是**最容易压垮网关**的一步——输入大、输出长（可达 24K token）、且要求严格 JSON；它决定整套流程能否跑通。

## 4. 规模 / 吞吐估算（单本 1300 章 / 430 万字）

- 调用次数：约 **1,700 ~ 2,100 次 / 本**。
- Token 总量：粗估 **20M ~ 30M tokens / 本**（输入约 15~18M，输出约 6~10M，含多轮重复阅读全书）。
- 期望速度：希望 **4~6 小时**跑完一本书的识别阶段（可接受 overnight）。
  - 折算需要持续吞吐约 **80k~120k tokens/分钟**、**≥ 8~15 次请求/分钟**（重结构化请求占比高，主要看 token 吞吐而非单纯 QPS）。
- 峰值并发：**16~32**（我们会在客户端限并发；请网关保证这个量级不被限流）。

---

## 5. 当前遇到的问题（供网关参考）

1. **非流式 60s 超时 → 504**：复杂对白归属请求常在 60s 才生成完，之前被网关 60s 切断（`openresty 504`）。已把网关 `proxy_read_timeout` 改到 1d 后恢复正常（单次重请求约 30~150s）。**请保持长超时（≥600s）或支持流式。**
2. **最大输出被截断**：若网关单次输出上限 < 24K token，对白归属会截断成非法 JSON。
3. **限流用 2062/402/504 表达**：请用标准 **429 + Retry-After** 表达限流；不要用 504/402 混淆（我们据此做退避）。
4. **内容审核过严**：正常小说文本偶发被判敏感（422），建议使用面向创作/小说场景、审核可配置的模型。
5. **思考模式**：开启思考会让长请求更慢更易超时；请支持显式关闭并真正生效。

## 6. 建议的模型画像（可选两种）

- **A. 强理解 + 长上下文型**（用于：角色识别、去重、书籍资料、音色推荐）
  - 上下文 ≥128K、中文长文理解强、指令遵循好、输出 8K~16K。
- **B. 高吞吐结构化抽取型**（用于：对白归属、情绪、润色 —— 占绝大多数调用）
  - 稳定输出 **严格 JSON**、单次输出 ≥24K、支持高并发、对长中文 prompt 友好、**默认关闭思考**、延迟可接受（单请求 30~180s）。

> 如果网关能用一个「分层/路由」模型（按请求自动选合适上游）同时满足 A、B 两类，最省心。

---

## 7. 一句话给网关的「采购清单」

> 需要 **OpenAI 兼容**、**上下文 ≥128K**、**单次最大输出 ≥24K token**、**支持关闭思考**、**非流式单请求可跑 3~5 分钟不超时（proxy 超时 ≥600s）**、**支持 ≥16~32 并发**、**限流用 429+Retry-After**、**SQL/JSON 结构化输出稳定**、**中文小说理解好且审核不过度** 的模型/网关。核心用途是「对海量中文长文做严格 JSON 结构化抽取」，其中「对白归属」是压力最大的一步（大输入 + 最长 24K 输出 + 严格 JSON）。
